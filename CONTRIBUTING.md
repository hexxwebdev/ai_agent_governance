# Contributing

Thank you for your interest in improving the AI Agent Governance project.

The purpose of this repository is to provide a reusable, vendor-neutral governance framework that helps AI agents and software developers build secure, maintainable, and consistent software.

Contributions are welcome and appreciated. The long-term vision of this project, however, is intentionally conservative. Stability, clarity, and broad applicability are prioritized over rapid expansion.

---

# Guiding Principles

Contributions should strive to keep the project:

* AI agent friendly
* Vendor neutral
* Technology agnostic
* Simple and easy to adopt
* Focused on long-lived engineering guidance
* Practical rather than overly prescriptive
* Consistent across all governance documents

---

# Project Scope

This repository contains reusable engineering governance.

Examples include:

* Engineering Principles
* Architecture Principles
* Development Standards
* Security Standards
* Database Standards
* API Standards
* Logging Standards
* Event Logging Standards
* Code Review Checklist

Project-specific implementation details, business logic, workflows, or application documentation should not be added to this repository.

---

# Before Submitting Changes

Before opening a pull request, please ensure your contribution:

* Maintains a vendor-neutral approach.
* Avoids references to specific AI tools, IDEs, cloud providers, frameworks, or programming languages unless they represent broadly accepted industry practices.
* Preserves compatibility across a wide variety of software projects.
* Keeps guidance concise, practical, and actionable.
* Avoids unnecessary complexity.
* Does not introduce project-specific workflows or business requirements.
* Does not duplicate existing guidance.

---

# Project Direction

This project is intentionally opinionated.

Not every proposed contribution will be accepted. While all suggestions are appreciated, changes should support the long-term goals of the project rather than individual preferences or technologies.

Changes are most likely to be accepted when they:

* Improve clarity.
* Improve maintainability.
* Improve consistency.
* Improve security.
* Reflect broadly accepted engineering practices.
* Remain useful across many software projects.

Changes are unlikely to be accepted when they:

* Introduce vendor-specific guidance.
* Focus on a single programming language or framework.
* Add unnecessary complexity.
* Duplicate existing standards.
* Represent implementation details rather than governance.
* Change the overall philosophy or direction of the project.

The project maintainer reserves the right to decline contributions that do not align with the project's goals, design principles, or long-term vision.

---

# Documentation Style

Documentation should:

* Use clear and concise language.
* Prefer simple recommendations over rigid rules where appropriate.
* Organize content using consistent headings and formatting.
* Remain readable by both AI agents and human developers.
* Be written in Markdown.

---

# Reporting Issues

Bug reports, suggestions, and constructive discussions are welcome.

When reporting an issue, please include:

* A clear description of the problem.
* The affected governance document.
* The reason the current guidance should be improved.
* A proposed improvement, when possible.
